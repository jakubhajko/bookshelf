# ADR-0015: Raw interaction events with optional attribution, not a universal preference score

## Status

Accepted (Recommender Phase 0). Extends the append-only
`interaction_events` design from application Phase 4 (spec §8.9).

## Context

Five candidate generators need behavioral evidence, and they need it
*differently*. ALS wants durable positive preference. Item-item CF wants
weighted seed books. Semantic profiling wants positive evidence plus
explicit negative evidence for repulsion. A future session generator would
want recent opens and search intent at high weight — evidence the
long-term generators should largely ignore.

The tempting simplification is one stored number per `(user, book)`: an
"interaction strength" every generator reads. It is wrong in a way that is
expensive to undo — it bakes one interpretation of the evidence into
storage, so changing how saves weigh against ratings becomes a data
migration instead of a config change, and the original signal that produced
the number is gone.

Phase 0 inspection found the raw-event substrate already exists and is
unused. `interaction_events` carries `surface`, `session_id`,
`recommendation_request_id`, `search_query_id`, `source_book_id` and
`rank_position` — all nullable, all correct, and **written by nothing**.
`interactions/service.py` accepts no attribution arguments at all.
`shelf_books.source_surface` exists and is threaded through both the
service and repository signatures, but no caller ever passes a value.
`EventType` has no `book_opened` member. The columns were provisioned by
Phase 4 for exactly this work and then left unfilled, so the schema barely
changes — the write paths do.

The recommendation-impression path has a real, currently-live defect worth
recording here because it determines whether impression data is
trustworthy: `recommendations/repository.py::create_impressions` is a plain
`session.add_all` against a table with `UNIQUE(request_id, book_id)`.
Re-fetching a persisted cursor page — which ADR-0007's design makes an
ordinary, expected thing for a client to do — inserts duplicate rows and
fails. Impression data cannot be relied on until that write is idempotent.

## Decision

Persist raw product actions and their provenance. Do not persist a derived
universal preference score. Generators interpret the same raw evidence
differently, at read time, under versioned configuration.

Concretely:

- Add `book_opened` as a raw event for *intentional* book-detail opens,
  written through a dedicated authenticated event endpoint. `GET
  /books/{id}` stays side-effect free — a read endpoint that silently
  writes is untestable, uncacheable, and fires on prefetches and crawlers.
- Populate the six existing attribution columns from a single shared,
  typed, optional `InteractionAttribution` shape used by every write path
  that accepts it, rather than six loose fields redeclared per endpoint.
- Attribution is always optional. An action taken from a non-recommendation
  surface carries none, and that is a valid, complete record — not a
  degraded one. Never infer attribution that is not known.
- Add a short-lived browsing `session_id`, generated by the frontend, held
  in `sessionStorage` (per tab), rotated after ~30 minutes of inactivity.
  It is never the 30-day authentication `sid`: conflating a security
  credential with an analytics correlator would both weaken the credential
  and make "session" mean two incompatible things.
- Persist meaningful *submitted* searches in a dedicated `search_queries`
  table, and support search-query → book-open attribution. Debounced
  autocomplete requests are not searches and are not logged.
- Populate `shelf_books.source_surface` when the save's origin is known,
  without changing shelf-membership semantics.
- Make recommendation-impression writes idempotent.

Signal semantics are fixed policy, recorded here because they determine
what the data means:

- **An impression without an open is exposure, not a negative preference.**
  Treating "shown but not clicked" as dislike is the single most common way
  to poison an implicit-feedback dataset — position, layout and simple
  non-attention all masquerade as rejection.
- **Not Interested is a strong explicit negative** and a hard exclusion
  where product rules require it.
- **Historical rating `0` is an implicit positive**, never a negative, and
  historical data has no timestamps — recency must never be invented for
  it.
- **Onboarding taste seeds are neither ratings nor shelf saves** (ADR-0019).

No dwell time, hover, mouse movement or scroll-depth instrumentation is
added. It is noisy, privacy-adverse, and explicitly out of scope
(`RECOMMENDER_SPECIFICATION.md` §29).

## Alternatives considered

- **One stored ML interaction score per (user, book)** — rejected, see
  Context. Destroys the evidence that produced it and turns tuning into
  migration.
- **Make `GET /books/{id}` record the open** — rejected. Hidden write side
  effects on a read route fire on prefetch and non-intentional navigation,
  and make the endpoint untestable without asserting on writes.
- **Reuse the auth session `sid` as the browsing session** — rejected. A
  30-day credential is the wrong granularity for session recency, and
  putting a security token into analytics attribution widens its blast
  radius for no benefit.
- **Log every debounced autocomplete request as a search** — rejected. It
  would record keystroke prefixes rather than intent, and drown genuine
  query signal in noise.
- **Treat impression-without-open as a negative** — rejected, see Decision.
- **Add viewport-visibility impressions now** — deferred (already deferred
  once by ADR-0007). Delivery-time impressions remain the V1 definition.

## Consequences

- Every generator must state, in versioned configuration, how it
  interprets raw evidence. There is no "the" preference value to read, by
  design.
- Attribution coverage will be partial and must be handled as such:
  analysis and any future learned ranker have to tolerate rows where the
  origin is genuinely unknown rather than treating null as a category.
- Recommendation request/result/impression rows grow with usage.
  ADR-0007 already bounds batches with `expires_at`; a retention and
  cleanup policy must be documented (recommender Phase 1) without
  introducing a background-job stack — `make cleanup-sessions` is the
  established precedent for this class of maintenance.
- The data collected here is deliberately sufficient for a future
  session-aware generator and a learned ranker. Neither is built in V1;
  instrumenting first is the point.
- New personal-behavior data (searches, opens, session correlators) falls
  under the existing security/privacy rules: never logged, never returned
  in diagnostics, never exposed beyond the owning user.
